# Техническое задание для Codex: JAVAKHETI MEAT — рабочее название

Версия: 1.0 • Дата: 14.10.2026 • Статус: проектное ТЗ, не подтверждение реализации.

## 0. Цель
Создать работающий mobile-first интернет-магазин свежего мяса, полуфабрикатов, деликатесов и сопутствующих товаров для Ахалкалаки (Грузия), с архитектурой для расширения на Ниноцминду, Ахалцихе и другие регионы. Три полноценных языка: русский (ru), грузинский (ka), армянский (hy). Визуальный уровень премиальной мясной лавки, коммерческая логика проверенных модулей из `xugushik-source/Pivka-dlya-ryvka-`. Не копировать чужой дизайн, исходники или фотографии без прав.

Не выдумывать, что именно в нём реализовано. Составить таблицу вдохновения: паттерн, URL, что адаптируем, ограничения по лицензии.

## 2. Строгие ограничения
- Создать **отдельный** репозиторий/проект, не изменять Pivka, DENT-ELIT, существующие main/production, DNS и публичные сайты.
- Работать в feature-ветке. Не пушить в main, не деплоить публично, не включать платные сервисы без отдельного разрешения владельца.
- Не запускать настоящие платежи, рассылки, покупки, реальные заказы, реальные доставки.
- Никогда не хранить банковские реквизиты, ключи и персональные данные в Git; `.env.example` без секретов.
- Тестовые цены, курсы, адреса, реквизиты и изображения явно помечать DEMO. Никаких выдуманных реальных остатков.
- Для алкоголя предусмотреть выключенный feature flag, возрастную проверку и отдельную правовую проверку для конкретного продавца, региона, доставки и способа оплаты; до подтверждения не включать продажу.
- Российская оплата — **не эквайринг** и не банковская интеграция: ручной перевод по реквизитам, загрузка чека, ручная проверка.

## 3. Технология и организация
Предпочтительно Next.js + TypeScript + Tailwind CSS + доступная UI-библиотека + PostgreSQL/Supabase с RLS + объектное хранилище для чеков/изображений + Playwright/Vitest. Если репозиторий или инфраструктура требуют иной стек — сначала описать обоснование в `docs/ARCHITECTURE.md`. Серверный источник истины для денег, остатков, заказов и статусов. Миграции и seed-данные. Разделить storefront, admin, server/domain, database, i18n, media.

Обязательные файлы: `AGENTS.md`, `README.md`, `docs/SPEC.md`, `docs/RESEARCH.md`, `docs/ARCHITECTURE.md`, `docs/PLAN.md`, `docs/TEST_REPORT.md`, `.env.example`. `docs/PLAN.md` — живой план с Progress, Decision Log, Discoveries, Outcomes.

## 4. Бренд и UX
Премиальная гастрономическая эстетика: насыщенные естественные фотографии, тёплая светлая основа, глубокие тёмные акценты, выразительная типографика, много воздуха, тактильные детали. Без шаблонного «супермаркета» и без копирования чужого брендинга. Сначала мобильный дизайн 360–430px, затем планшет и десктоп.

Обязательные интеракции:
- полноэкранный первый экран с выразительной типографикой и лицензированной фотографией;
- аккуратные scroll transitions, смена фотографий, плавные reveal/scale/parallax эффекты; мягкие shared-element transitions только там, где технически надёжно;
- выдвижная **шторка** (bottom sheet на мобильном, side drawer на десктопе) для корзины, вариантов товара, выбора города, языка, фильтров и оплаты;
- sticky mini-cart, плавное добавление товара, тактильная обратная связь;
- доступная анимация с `prefers-reduced-motion`, без блокирования кликов и прокрутки; не ухудшать Core Web Vitals;
- корректная клавиатурная навигация, фокус, контраст, размеры touch targets;
- hero, каталог, категории, подборки, карточка товара, конструктор заказа, корзина, checkout, статус заказа, избранное, повтор заказа, профиль, FAQ, доставка, контакты, юридические страницы;
- фирменные наборы с редактором компонентов; подарок/прогресс до порога; контекстные допродажи, без повторного предложения уже включённых продуктов.

## 5. Языки и география
Языки RU/KA/HY на всём пути: категории, названия, состав, аллергенные предупреждения, кнопки, ошибки, email/SMS-шаблоны (без отправки), админские поля для перевода. Переключатель языка сохраняет текущую страницу/корзину; fallback на русский с отметкой недостающего перевода в админке. Правильные Unicode-шрифты и SEO `hreflang`.

Модель `regions`, `delivery_zones`, `store_locations`, `fulfillment_locations`, `regional_prices`, `regional_inventory`, `regional_promotions`. Первый активный город: Ахалкалаки; Ниноцминда и Ахалцихе заведены как неактивные шаблоны. Через админку владелец включает город, расписание, радиусы/зоны, ассортимент, цены, минимальную сумму, стоимость доставки, доступные методы оплаты и часы производства. Не обещать время доставки без настроенных параметров.

## 6. Ассортимент и товарная модель
Категории: свинина (шея, корейка, карбонад, лопатка, окорок, рёбра, грудинка, вырезка); говядина (мякоть, рёбра, антрекот, грудинка, голяшка, фарш, мясо для хашламы); баранина (корейка, нога, лопатка, рёбра, мякоть); курица (тушка, бедро, голень, крыло, грудка, филе); шашлык и маринады; люля-кебаб; котлеты, купаты, домашние колбаски, тефтели, долма/толма; блюда для запекания; деликатесы (плоский армянский мясной суджук, бастурма); соусы, аджика, ткемали, сацебели, лаваш, овощи, зелень, соленья, специи; уголь, шампуры, решётки; безалкогольные напитки. Алкогольные товары (вино, водка, коньяк, чача, пиво) только за отключённым флагом до правового согласования.

Каждый SKU: уникальный ID, 3 перевода, категория, изображения и права, единица измерения, шаг веса (например 0.1 кг), минимальный вес, цена за кг/шт., налоговая модель, закупочная себестоимость, остаток, срок годности, температурный режим, аллергены, статус доступности, возможность приготовления, региональные переопределения. Поддержать **примерный вес**: предварительная сумма, фактический вес при сборке, правило допустимого отклонения и необходимость согласования изменения цены с клиентом; не увеличивать оплаченный заказ молча.

Опции подготовки: нарезать для шашлыка, оставить куском, сделать фарш, сформировать котлеты/люля, выбрать маринад/остроту/лук, указать желаемое время. Для купат — тип мяса и специи. Для деликатесов — целый батон, на вес, нарезка; контроль партий и безопасности.

## 7. Наборы, акции, лояльность
Наборы «Шашлык на четверых», «Большой семейный стол», «Люля на мангал», «Домашний ужин», «Стейк-вечер», «Мясо на праздник». Каждый набор — состав из реальных SKU и количеств, цена, себестоимость, валовая маржа, складская доступность и возможность замены компонента. Контекстные допродажи: к шашлыку — лаваш, соус, овощи, уголь; к котлетам — гарнир, специи. Подарочные пороги (только наивысший достигнутый), подарки списывают реальные остатки; настраиваемые промо, бонусы и лояльность/PASS как отключаемый модуль. Повтор заказа с актуализацией цен и остатков. Подарок другу как опциональный этап 2.

## 8. Корзина и оформление
Гостевой checkout без обязательной регистрации; телефон, имя, город, адрес, комментарий, время, состав и итог. Хранить корзину локально и безопасно восстанавливать после перезагрузки. На сервере пересчитывать цену, вес, скидку, доставку, регион, остатки, надбавку. Создавать уникальный заказ идемпотентно. Если платёж/загрузка чека не завершены, корзину **не очищать**.

## 9. Российская оплата — точная бизнес-логика
Метод: «Оплата из России / перевод по реквизитам». Без эквайринга, платёжного API и интеграции с банком.
- Формула: `payable_gel = round((items_gel + delivery_gel - discount_gel) * 1.15, 2)`; точное округление и порядок применения скидок документировать. `payable_rub = round(payable_gel * admin_configured_rub_per_gel, 2)`; курс, дата/время, исходная сумма, надбавка 15% и итог фиксируются в снимке заказа. Не брать «курс из интернета» без источника и правил обновления.
- Надбавка 15% действует **только** для этого метода, редактируется в админке, показывается отдельной строкой до подтверждения. В зависимости от договорных/правовых требований формулировку для покупателя согласовать до публичного запуска.
- Показывать реквизиты, получателя, назначение платежа с номером заказа, кнопку «Копировать», инструкцию перевода, таймер только если реально настроено время резерва.
- Кнопка «Я оплатил» открывает загрузку JPEG/PNG/WEBP/PDF (ограничения размера, MIME, сканирование, приватное хранилище, signed URLs, запрет публичного доступа). Не требовать лишних персональных данных из скриншота; подсказка скрыть баланс и ненужные операции.
- После **успешного серверного сохранения** заказа, вложения и события `PAYMENT_PROOF_SUBMITTED` — очистить локальную корзину, закрыть payment drawer, показать `Чек получен. Заказ №... ожидает проверки оплаты` и страницу статуса с кодом восстановления. При ошибке загрузки не очищать корзину, разрешить повторить без дубликата заказа.
- В админке немедленно появляется `PAYMENT_REVIEW_REQUIRED`, карточка заказа, сумма GEL/RUB, курс, +15%, время, вложение, действия `Подтвердить поступление`, `Отклонить`, `Запросить другой чек`. Уведомление внутри админки; внешние push/email/Telegram — только после отдельного подключения и разрешения.
- Скриншот **не равен доказанной оплате**. До проверки состояние `PAYMENT_PROOF_SUBMITTED / AWAITING_VERIFICATION`, не `PAID`. После проверки владельцем `PAID`, затем `CONFIRMED/PREPARING`.
- Обязателен аудит: кто, когда и почему изменил статус; запрет повторного подтверждения, идемпотентность, защита от двойного заказа.
- Другие методы (наличные при получении, грузинский перевод) — отдельные конфигурируемые сценарии, не смешивать с российской надбавкой.

## 10. Производство, склад, доставка
Рабочая очередь: NEW → PAYMENT_REVIEW_REQUIRED (если перевод) → CONFIRMED → PREPARING → READY → OUT_FOR_DELIVERY → DELIVERED; альтернативные CANCELLED/REFUNDED/FAILED. Производственные задания с рецептурой, весом, компонентами, временем и сотрудником. Резервы ингредиентов, списание при изготовлении, партии/сроки годности, журнал движений, причины списаний. Запрет отрицательных остатков без явного админского разрешения. Курьерская очередь, адреса и статусы, зоны, тарифы, ETA только при настройке.

## 11. Админка владельца
Роли OWNER, ADMIN, STAFF, DRIVER с RLS и проверкой полномочий на сервере. Главный экран: новые заказы, **чеки на проверку**, очередь производства, доставка, остатки, выручка, валовая прибыль, расходы, проблемы. Отдельные страницы: каталог, цены по регионам, фото/лицензии, рецептуры, партии, закупки, наборы, промо, подарки, CRM клиентов, повторные заказы, города, языки/переводы, курсы GEL/RUB, методы оплаты/реквизиты, аудит, настройки. Никаких секретов на клиенте.

## 12. Голосовой продавец
Заметная, но **отключённая** функция за `VOICE_SELLER_ENABLED=false`. Визуальная кнопка и нейтральный текст «Скоро появится». Архитектура для будущих RU/KA/HY, рекомендаций из реального каталога, без выдумывания цены и остатков. Не отправлять звук и не вызывать платный API, пока не включено владельцем.

## 13. Безопасность и правовые требования
Проверить местные требования к пищевой безопасности, холодовой цепи, срокам хранения, маркировке, потребительским документам, защите персональных данных, оплате российскому ИП за товары в Грузии и возрастным ограничениям алкоголя. Не объявлять соответствие без юридической проверки. Разделение доступа к чекам, retention policy, удаление по правилам, CSRF/XSS/SQLi защита, rate limiting, антиспам, журнал действий, резервные копии. Не принимать реальные платежи до утверждения реквизитов и юридической модели.

## 14. SEO, качество и производительность
SSR/metadata, sitemap, robots, schema.org Product/Offer с реальной доступностью, `hreflang`, понятные URL. Оптимизированные изображения, responsive sizes, lazy load, правильный alt, отсутствие layout shift. WCAG 2.2 AA по возможности; reduced motion; быстрый first interaction на мобильных сетях. Ошибки на всех 3 языках. Логирование без секретов и лишних персональных данных.

## 15. Этапы и критерии приёмки
**Этап 0 — аудит и план:** исследование Pivka, референсов, Codex best practices; создать архитектуру, реестр ассетов и `docs/PLAN.md`. Не останавливаться на плане, если разрешено продолжить в текущем задании.
**Этап 1 — рабочая витрина:** 3 языка, Ахалкалаки, категории, карточки, фото с лицензиями/placeholder, шторки, анимации, корзина, наборы, допродажи. Демо локально.
**Этап 2 — сервер и заказы:** БД, RLS, региональные цены, остатки, заказ, статус, upload чека, +15%, админская проверка. Полный e2e сценарий без денег.
**Этап 3 — производство и управление:** задания, рецептуры, склад, доставка, CRM, аналитика и прибыль.
**Этап 4 — готовность к пилоту:** тесты, аудит безопасности, оптимизация, переводы, документация, список внешних подключений и юридических проверок. Публичный запуск — только отдельным разрешением.

Обязательные автотесты: расчёт 15%, RUB-конвертация и округление, переключение метода оплаты, недоступный SKU, гонки резервирования, загрузка файла и отказ, повторная отправка, восстановление корзины при сбое, очищение только после успешной фиксации, неподтверждённый чек не превращается в PAID, права ролей, языки, переключение города, отсутствие реальных внешних вызовов. Зафиксировать скриншоты и отчёт тестов.
